# RPS Arena v0.1.1 Plan

`v0.1.1` is the first patch release on the public `v0.x` release track. It should be deliberately focused: improve reliability and user-facing quality without turning a patch release into a platform or architecture rewrite.

## Release objective

Deliver a stable follow-up to `v0.1.0` with targeted fixes, stronger regression coverage, and release documentation that accurately describes what is shipped.

## Priority 1 — data safety

- Harden backup/import validation without silently changing the `RPSARENA_BACKUP|1` contract.
- Improve user-facing failure handling for malformed or incompatible local data.
- Add or strengthen regression tests for persistence recovery and state synchronization.
- Keep reset/history-clearing operations explicit and reversible where the existing architecture can support that safely.

## Priority 2 — gameplay reliability

- Verify deterministic CPU behavior across repeated seeded matches.
- Strengthen ruleset and match-state invariant coverage.
- Fix any reproducible gameplay regressions discovered after `v0.1.0`.
- Avoid introducing a real network transport into the patch release.

## Priority 3 — UI, accessibility, and localization

- Expand focused Android and desktop UI regression coverage.
- Verify keyboard navigation and semantic labels on supported desktop flows.
- Verify reduced-motion behavior where applicable.
- Preserve localization key/placeholder parity across all supported catalogs.

## Priority 4 — platform robustness

- Keep Android, iOS/iPadOS, desktop, and Web behavior aligned with the offline-first contract.
- Address release-blocking build or packaging regressions found after `v0.1.0`.
- Keep signing credentials and private distribution configuration outside the public repository.

## Priority 5 — documentation and maintenance

- Keep README claims synchronized with actual shipped behavior.
- Keep release and maintenance guides consistent with the public `v0.x` release track.
- Record any intentional limitations rather than implying unsupported production behavior.

## Explicitly out of scope

These items should remain separate from the `v0.1.1` patch unless a release-blocking defect requires them:

- Real LAN/private-room networking.
- Cloud accounts or synchronization.
- Analytics or advertising SDKs.
- Large architecture replacements.
- Production signing credentials.
- Unrelated large feature sets.

## Entry criteria

Work should be based on the exact `main` revision selected for the public `v0.1.0` release. If `v0.1.0` has not yet been tagged, finalize that release first so the patch has a clean public baseline.

## Exit criteria

Before tagging `v0.1.1`:

1. All intended changes are merged into `main` through reviewable commits.
2. Repository formatting and documentation checks pass.
3. Secret, privacy, version, and localization checks pass.
4. Shared, Android, desktop, Web, iOS, and Rust checks required by the release pipeline pass where applicable.
5. Security and CodeQL checks are green on the exact final release revision.
6. Release artifacts and SHA-256 checksums are generated and verified where configured.
7. The release notes are reviewed against the actual diff from `v0.1.0`.
8. Tag `v0.1.1` points to the exact validated release revision.

## Commit discipline

Use small, meaningful commits such as `fix:`, `test:`, `docs:`, `build:`, `ci:`, and `refactor:` where appropriate. Do not create empty or cosmetic commits solely to inflate the repository's commit count.
