# RPS Arena v0.1.3 Release Plan

## Purpose

`v0.1.3` is the next public patch release after the published `v0.1.2` baseline. It should improve product quality without weakening the offline-first, privacy-conscious architecture.

## Public version track

- Previous public release: `v0.1.2`
- Next public release: `v0.1.3`
- Target branch: `main`
- Release type: patch/development release
- Recommended GitHub status: stable release when all gates are genuinely green

The repository also contains historical/internal `v2.5.x` versioning. The public release track remains `v0.x`; do not change package metadata merely to mirror the historical internal version.

## Proposed scope

### 1. Data integrity and recovery

- Continue hardening local persistence and backup recovery.
- Add regression coverage for state preservation when imports fail.
- Keep `RPSARENA_BACKUP|1` compatibility unless a deliberate migration is designed and tested.
- Keep malformed, oversized, inconsistent, or unsupported local data from being partially applied.

### 2. Gameplay correctness

- Expand deterministic CPU regression coverage across supported rulesets and match modes.
- Verify match-state invariants around round completion, scoring, resets, and configuration transitions.
- Prefer small correctness fixes backed by focused tests over broad gameplay rewrites.

### 3. Accessibility and UI quality

- Strengthen semantic labels and keyboard/navigation regression coverage where supported.
- Improve user-visible error and recovery states without exposing sensitive local data.
- Preserve localization key/placeholder parity.

### 4. Cross-platform reliability

- Re-run release-critical Android, desktop, Web, iOS, and Rust validation against the exact candidate.
- Fix reproducible platform-specific regressions that fit the patch scope.
- Keep platform signing credentials and store secrets outside the repository.

### 5. Release engineering

- Keep version checks authoritative and fail closed on inconsistent metadata.
- Verify Security and CodeQL on the exact release head.
- Generate only reproducible/verified release artifacts and SHA-256 checksums where the packaging workflow supports them.
- Make release notes describe the actual diff, not planned or historical features.

## Explicitly deferred

The following should remain outside this focused patch unless separately approved and security/privacy reviewed:

- Real LAN/private-room networking.
- Cloud accounts or synchronization.
- Analytics or advertising SDKs.
- Unnecessary Android network permissions.
- Production signing credentials in source or CI configuration.
- Large architecture replacements.
- Unrelated feature expansion.

## Commit discipline

Use focused, reviewable commits such as `fix:`, `test:`, `docs:`, `ci:`, `build:`, and `refactor:`. Maximize **meaningful** commit history by separating independently reviewable concerns; never create empty, cosmetic, or duplicate commits solely to increase the commit count.

## Release gates

Before tagging `v0.1.3`:

- [ ] `v0.1.2` remains the verified public baseline.
- [ ] Every claimed change is present on the candidate head.
- [ ] Formatting and documentation checks pass.
- [ ] Secret/privacy/version/localization checks pass.
- [ ] Shared tests pass.
- [ ] Applicable Android, desktop, Web, iOS, and Rust checks pass.
- [ ] Security and CodeQL pass on the exact candidate.
- [ ] Release artifacts/checksums are generated and independently checked where configured.
- [ ] Release notes are reviewed against the actual `v0.1.2...candidate` diff.
- [ ] The `v0.1.3` tag points to the exact validated release revision.
- [ ] Post-tag release assets and generated source archives are verified.
